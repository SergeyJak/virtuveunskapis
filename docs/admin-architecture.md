# Админка: результат проверки архитектуры

Реализован вариант 1: встроенная админка Next.js и отдельный постоянный каталог данных для одного экземпляра сервера. Ограничение AGENTS.md на пять файлов снято по прямому указанию пользователя. Инструкция: [admin-setup.md](admin-setup.md). Ниже сохранены результаты первоначального исследования и сравнение вариантов.

## Текущее устройство

- Next.js 16, React 18, TypeScript, собственный CSS; статический экспорт не включён.
- Категории: kitchens, wardrobes, bathrooms; существующие URL и локализации необходимо сохранить.
- scripts/generate-project-manifest.mjs сканирует public/images/original-projects/sorted при установке, запуске разработки и сборке.
- data/site.ts импортирует сгенерированный JSON. Главная, портфолио, страницы проектов и sitemap используют этот список.
- Сейчас нет административной авторизации, загрузки файлов, базы посетителей или публичного сборщика событий.
- Новые изображения нельзя просто добавлять в JSON: следующая сборка перезапишет его.

## Предлагаемая реализация

Встроить /admin в существующий Next.js. Сохранить оформление публичного сайта и существующие проекты как исходный каталог. Добавить серверный слой данных и объединять исходный каталог с управляемыми проектами при чтении. Обновить главную, портфолио, страницы проектов и sitemap, чтобы опубликованные изменения появлялись без пересборки.

Раздел «Проекты»: выбор существующей категории, название, описание, несколько фотографий, обложка, порядок, публикация и скрытие. Исходные файлы не удалять при скрытии проекта. Загруженные файлы хранить вне исходников; выдавать через отдельный маршрут. Проверять формат по содержимому, размер и количество файлов, имена генерировать на сервере, исключить обход путей.

Вход: отдельный администратор, пароль из переменных окружения, проверка на сервере, подписанная ограниченная по времени HttpOnly/Secure/SameSite cookie, проверка Origin для изменений, ограничение частоты входа. Все административные API проверяют авторизацию независимо от интерфейса. Секреты не включать в клиентский код.

Раздел «Посетители» по образцу SergeyJak/inventory-app: уникальные посетители, сессии, просмотры, возвраты, переходы к контактам; периоды 7/14/30 дней и произвольные даты, поиск, страницы результатов, карточка посетителя с историей. Фиксировать источник/UTM, страницу входа, язык, устройство и браузер. События адаптировать к мебельному портфолио: просмотр страницы/проекта, выбор категории, переход к телефону/email. Админку исключить из отслеживания. Ограничить входящие события, очищать URL от лишних параметров, ограничить срок хранения. Данные посетителей доступны только администратору. География — только при наличии доверенных данных хостинга или локальной GeoIP-базы, без выдуманных значений.

## Варианты хранения

1. Next.js + постоянный диск: минимум новой инфраструктуры, без новых зависимостей; подходит для одного экземпляра сервера. Нужны атомарные записи, сериализация операций, ограничение объёма аналитики и резервное копирование. Не подходит для эфемерной файловой системы или нескольких реплик.
2. Next.js + MongoDB + объектное хранилище: ближе к inventory-app и подходит для нескольких реплик; требует подключения базы, хранилища и одобрения новых зависимостей.
3. Отдельная CMS и аналитика: больше внешних сервисов, настройки и обслуживания; для текущей задачи преимуществ перед встроенной админкой не обнаружено.

Рекомендация: встроенная админка Next.js. Конкретное постоянное хранилище выбрать после проверки фактического хостинга. До этого не подключать временное хранилище как производственное.

## Проверка результата

Проверить вход/выход и запрет неавторизованных API; загрузку и публикацию фотографий во всех трёх категориях; появление проекта в портфолио, на главной и по прямой ссылке; сохранность данных после перезапуска; сбор событий и фильтры посетителей; отсутствие доступа к аналитике у публичного клиента; ограничения загрузок и событий. Выполнить TypeScript-проверку, production build и браузерные проверки на desktop/mobile.

## Объём и ограничения

Потребуются новые страницы и стили админки, серверные модули авторизации и хранения, API, клиентский сборщик событий, изменения публичных страниц/layout/sitemap, инструкции конфигурации и проверки. Это больше пяти файлов. AGENTS.md требует остановиться и сообщить при таком объёме. .agents/RULES.md отдельно запрещает новые зависимости без одобрения.

На этапе проверки продуктовый код не изменён. Развёртывание и переменные окружения ещё не настроены. Фактическая конфигурация хостинга не установлена.
